# ADR 0005：静态导出体积上限从 8 MB 抬到 10 MB

- 日期：2026-11-10
- 状态：已采纳
- 相关：`web/scripts/verify-build.mjs`、ADR 0004（多城配置化）、`docs/plan-p1a.md` 六之二

## 背景

8 MB 这个数是在 P0（只做上海）时定的：当时 `out/` 3.96 MB，留一倍余量，目的是防「底图/字体/死资产」这类体积失控。

P1a 把四城（上海 / 广州 / 成都 / 合肥）都做出来后，体积逐轮上涨：

| 阶段 | `out/` | 说明 |
| --- | --- | --- |
| P0 收尾 | 3.96 MB | 单城 + 自建底图 |
| P1a-6.1 四城数据 | 7.14 MB | 四城 `lines/station/segment/transfer` + 上海底图 |
| P1a-6.2/6.3 | 7.22–7.23 MB | 四页 + sitemap + 切换器 |
| P1a-6.4 三城轻底图 | **7.91 MB** | 广州 227 KB / 成都 242 KB / 合肥 237 KB |

7.91 MB 距 8 MB 只剩 90 KB，任何后续改动（6.5 的校验产物、6.6 的部署元信息、以后加第 5 座城）都会直接撞线。

## 决策

把 `verify-build.mjs` 的上限从 **8 MB 改为 10 MB**。

## 理由

1. **8 MB 不再代表用户成本。** 它是「全部产物的未压缩总量」，但页面是按城懒加载的：打开广州页只取 `data/gz/` 那 1.75 MB（gzip ≈400 KB），上海的 1.88 MB 不会被下载。用总量卡单城体验，口径本身就是错的。
2. **真实首屏指标远低于预算。** 四城全量 gzip 后 ≈1.47 MB；单城首屏（HTML + JS + 当前城数据）在 6.2 实测约 0.75 MB。
3. **10 MB 仍能挡住失控。** 它比当前值高 26%，足以容纳再一城（≈1.9 MB 数据 + 0.24 MB 底图）与校验产物；而真正该防的东西（maplibre 副本 5.14 MB、dev 构建残留、字体 PBF）都有独立断言，不依赖这个总数。
4. **可回退。** 一旦将来改成「按需从远端拉全量数据」或多城分片，口径要重算，届时按本文重议。

## 备选方案与不采用的原因

| 方案 | 不采用的原因 |
| --- | --- |
| 保持 8 MB，把 `segment.geojson` 拆片 | 广州 1.25 MB 是最大单文件，拆片能省约 0.4 MB，但引入「区间几何按需加载」的运行时逻辑，与 P1a 的「静态、零运行时外部请求」冲突 |
| 把 GeoJSON 转成 TopoJSON/压缩格式 | 需在前端引入解码器，首屏 JS 变大，净收益不明 |
| 削减底图细节（邻市界 10 → 6 等） | 三城底图合计才 706 KB，砍到一半只省 0.35 MB，却让地理参照变差 |
| 不设上限 | 失去防回归能力 |

## 影响

- `verify-build.mjs` 的断言文案改为 `< 10 MB`，失败时打印实际值与 gzip 估算。
- 后续每加一城，先看这一项是否接近 10 MB；超过时按上表重新评估。
