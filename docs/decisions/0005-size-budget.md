# ADR 0005：静态导出体积上限（8 → 10 → 80 MB）

- 日期：2026-11-10（初版 10 MB）；2026-11-16 修订（P1b 54 城，抬到 80 MB）
- 状态：已采纳
- 相关：`web/scripts/verify-build.mjs`、ADR 0004（多城配置化）、`docs/plan-p1a.md` 六之二、`docs/p1b-cities.md`

## 背景

8 MB 这个数是在 P0（只做上海）时定的：当时 `out/` 3.96 MB，留一倍余量，目的是防「底图/字体/死资产」这类体积失控。

P1a 把四城（上海 / 广州 / 成都 / 合肥）都做出来后，体积逐轮上涨：

| 阶段 | `out/` | 说明 |
| --- | --- | --- |
| P0 收尾 | 3.96 MB | 单城 + 自建底图 |
| P1a-6.1 四城数据 | 7.14 MB | 四城 `lines/station/segment/transfer` + 上海底图 |
| P1a-6.2/6.3 | 7.22–7.23 MB | 四页 + sitemap + 切换器 |
| P1a-6.4 三城轻底图 | **7.91 MB** | 广州 227 KB / 成都 242 KB / 合肥 237 KB |
| UX 阶段 3/5 | **8.38 MB** | 总览页（181 KB）+ 校验产物 |

7.91 MB 距 8 MB 只剩 90 KB，任何后续改动（6.5 的校验产物、6.6 的部署元信息、以后加第 5 座城）都会直接撞线。

## 决策

把 `verify-build.mjs` 的上限从 **8 MB 改为 10 MB**（P1a），P1b 全量 54 城时再抬到 **80 MB**，并新增一条「单城数据 < 5 MB」的独立断言。

## 理由

1. **8 MB 不再代表用户成本。** 它是「全部产物的未压缩总量」，但页面是按城懒加载的：打开广州页只取 `data/gz/` 那 1.75 MB（gzip ≈400 KB），上海的 1.88 MB 不会被下载。用总量卡单城体验，口径本身就是错的。
2. **真实首屏指标远低于预算。** 四城全量 gzip 后 ≈1.47 MB；单城首屏（HTML + JS + 当前城数据）在 6.2 实测约 0.75 MB。
3. **10 MB 仍能挡住失控。** 它比当时值高 26%，足以容纳再一城与校验产物；而真正该防的东西（maplibre 副本 5.14 MB、dev 构建残留、字体 PBF）都有独立断言，不依赖这个总数。
4. **可回退。** 一旦将来改成「按需从远端拉全量数据」或多城分片，口径要重算，届时按本文重议。

## 备选方案与不采用的原因

| 方案 | 不采用的原因 |
| --- | --- |
| 保持 8 MB，把 `segment.geojson` 拆片 | 广州 1.25 MB 是最大单文件，拆片能省约 0.4 MB，但引入「区间几何按需加载」的运行时逻辑，与 P1a 的「静态、零运行时外部请求」冲突 |
| 把 GeoJSON 转成 TopoJSON/压缩格式 | 需在前端引入解码器，首屏 JS 变大，净收益不明 |
| 削减底图细节（邻市界 10 → 6 等） | 三城底图合计才 706 KB，砍到一半只省 0.35 MB，却让地理参照变差 |
| 不设上限 | 失去防回归能力 |

## 影响

- `verify-build.mjs` 的断言文案改为 `< 10 MB`，失败时打印实际值与 gzip 估算。
- 后续每加一城，先看这一项是否接近 10 MB；超过时按上表重新评估。

## 修订 2026-11-16：P1b 全量 54 城，上限 10 → 80 MB

### 依据：按 4 城实测外推

当前 `out/` 8,785,512 B（8.38 MiB，4 城），构成：

| 部分 | 实测 | 54 城外推方式 | 外推值 |
| --- | --- | --- | --- |
| `data/<code>/` 四件 + 底图 | 5,771,808 B / 4 城 = **1,442,952 B/城** | × 54 | ≈ 77.9 MB |
| 每城页面 `index.html` | 14,970 B/页 | × 54 | ≈ 0.8 MB |
| 总览页 `/cities/` | 181,503 B（4 卡，63 条 path） | 每卡约 41,800 B，50 城新增 | ≈ 2.3 MB |
| 其余（JS/CSS/vendor/og/sitemap） | 2,832,201 B | 不随城市数增长 | 2.8 MB |
| **合计** | | | **≈ 83.8 MB（≈80 MiB）** |

也就是说 80 MiB 恰好是外推值本身——**这不是留了余量，而是把线画在预测值上**。

### 决策

1. 总上限 `SIZE_LIMIT_MB = 80`（对应 83,886,080 B）。
2. 新增 `CITY_DATA_LIMIT_MB = 5`：单城数据超过 5 MB 直接失败。总量是「54 城的平均值游戏」，某一城爆到 8 MB 也能被别的城稀释掉，必须单独卡。
3. 新增**预警线**（不判失败）：总量 ≥ 上限 90%（72 MB）时打印 `[注意] 体积已到上限的 90%`，让「快撞线」在构建日志里可见，而不是等最后一批突然变红。

### 为什么明知贴线还这么定

- 80 MB 是 P1b 决策时定的数（D5），且它确实能挡住「54 城 + 无脑堆资源」的量级失控。
- 真正的体积杠杆不在上限数字上，而在产物本身：坐标现在是 5 位小数（≈1 m），降到 4 位（≈11 m）在城市视野下看不出差别，`segment.geojson` 预计能省 **10–15%**（≈8–12 MB）——这是留给「批次推进到一半发现超线」时的第一手段，不必改前端任何代码。
- 预警线 + 单城断言让「什么时候该动手」变成可观测的事，而不是靠记忆。

### 已知风险与触发条件

| 风险 | 触发信号 | 处理 |
| --- | --- | --- |
| 54 城全量略超 80 MB | 预警线连续两批 > 90% | 先把坐标精度降到 4 位（改 `pipeline` 的量化参数并重跑），仍不够再谈抬上限 |
| 单城数据膨胀（如北京、上海大量支线） | `单城数据 < 5 MB` 变红 | 该城单独查 `segment.geojson`（是否把非本线 way 收进来）、必要时对该城降精度 |
| 总览页随城市数线性变重（54 城约 2.3 MB HTML） | 总览页 > 3 MB | 缩略图抽稀阈值从 `MIN_STEP 2.5` 提到 4、或在 30 城后改成按省分页 |
